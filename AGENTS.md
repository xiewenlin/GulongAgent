# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Locked product direction

- Visual target: `docs/design/selected-homepage-option-1.png` (玉瓷·东方算力).
- Preserve the ivory porcelain base, jade-green actions, pale-gold accents, restrained borders and shadows, and code-native light product UI.
- The first 1536 × 1024 viewport must contain the hero, 理解/组装/执行/进化 flow, and four-capability strip.
- Keep all theme variants light, calm, and legible; do not introduce gradients or a dark default theme.
- The partner-brand neural network may use a contained dark holographic canvas, matching the Second Brain visualization, while the surrounding homepage remains light and porcelain-toned.
- Partner-network rotation must pause only through its explicit control. Hovering a node or the canvas must never pause it, and the removed bottom status/instruction card must not be restored.
- Never use browser-native `alert`, `confirm`, or `prompt` dialogs. All confirmations and notices must use the shared porcelain-themed application dialog so typography, hierarchy, keyboard behavior, and mobile layout remain consistent across the website.
- Administrator filter bars must wrap into deliberate multi-row responsive grids before controls become cramped; action buttons, labels, pricing notes, and summary copy must never be clipped or forced into narrow character-by-character wrapping.
- The Web Agent creation-type selector contains only text, image, and video. `MiniMaxH3共享节点` is the first and default video model, with its full price formula visible in the model list; it must not reappear as a separate creation type.
- The Web Agent desktop workspace uses one page-level scrollbar. Its brand controls and model-cloud introduction stay in compact single-line toolbars, while the doubled-height composer floats at the viewport center and collapses into a restorable right-middle orb without losing the draft or attachments.
- The Web Agent H3 composer keeps a dashed reference-material upload card at the prompt editor's upper-left, the user-controlled magic-optimization switch centered inside the editor near its bottom edge, and every persistent generation parameter in one responsive no-wrap footer rail.
- Every non-administrator paid image or video request must atomically reserve wallet balance with an idempotency key and auditable ledger entry, return the charged and remaining balance, and refund a failed task exactly once. Administrators remain exempt.
- Paid PearAPI image/video calls are balance-funded for every non-administrator, including standard and subscribed users; membership status must not bypass or replace the atomic balance reservation.
- A successful charged MiniMaxH3 shared-node task settles exactly once: 50% goes to the bound execution-node user and the remainder goes to the platform administrator wallet, with separate idempotent ledgers. Administrator-created H3 tasks are exempt from both charging and revenue sharing.
- The short-video subscription is a separate `short_video_monthly` user type: fixed at CNY 5,999 monthly or CNY 59,999 yearly, offline payment only, and successful payment credits a 100% expiring package bonus so visible package funds equal twice the paid amount. Active users keep unlimited MiniMaxH3 shared-node generation; tasks consume remaining package funds and use the normal 50/50 settlement, then become zero-charge and zero-commission after the package funds reach zero. Expiry clears only the remaining package component, never unrelated recharge funds.
- MiniMaxH3 website tasks must stay linked to their originating Agent conversation. After claiming, the node reports `started` with an estimated total duration and then sends percentage progress updates; the conversation displays that progress until an idempotent assistant video result replaces it.
- MiniMaxH3 claim uses a same-account LAN load report: the polling node submits every bound LAN node's running-task count, estimated remaining total seconds, and capabilities; the server preserves FIFO task priority but assigns each task to the compatible node with the shortest projected workload. The worker DTO names that `assigned_node`, and only that node's binding token may callback. Legacy one-node claims remain temporarily compatible.
- Every MiniMaxH3 task has a server-computed estimate and `autoCancelAt` exactly ten estimates after creation (extended only when a trusted started callback reports a larger estimate). Active tasks past that deadline are atomically cancelled, refunded once, and surfaced through a Chinese notification that tells the requester to choose another video model. Tencent production runs the shared maintenance endpoint every minute.
- Generated MiniMaxH3 output video is private and retained for exactly 24 hours from successful completion. Preview and download always use requester/admin authorization plus short-lived signed URLs, and both the Agent card and administrator detail show the exact expiry and deletion state.
- The Web Agent chat may position the initial conversation snapshot at the newest message once, but polling, progress updates, streaming, and later replies must never force the reader back to the bottom. Each assistant workflow trace renders before that reply's content so the final answer remains directly below its processing flow.
- The Web Agent exposes one explicit magic-optimization switch and queues the user's choice with the original Chinese H3 prompt unchanged. When enabled, only a compatible MiniMax H3 Fast Video desktop execution node compiles the prompt locally immediately before inference; when disabled, it uses the original prompt. The node preserves the original prompt for audit, returns any locally generated `compiled_prompt` in its authenticated `started` callback, and fails the task without starting H3 when requested local optimization fails. Tasks requesting optimization must not be assigned to nodes that do not advertise `local_prompt_optimization_v1`.
- Authorization-management copy controls must remain clickable. If an unused legacy activation record cannot decrypt its original code, copying may securely reissue that unused code; used or revoked legacy records must never be silently reissued.
- Authorization management lists the user-defined desktop node name separately from the bound device name and supports safe fuzzy search across device name, MAC suffix (last six characters), and node name.
- Authorization management must show a complete activation code on one line, and its copy/action controls must never collapse into vertical one-character wrapping.
- MiniMax H3 ultra video (`minimax-h3-ultra-video`) and MiniMax H3 super video (`minimax-h3-super-video`) are independent licensed products. Codes must be generated and redeemed for one exact product, while the same computer may hold one license for each. A cross-product attempt must return a plain Chinese purchase-new-code explanation before hardware fingerprint validation.
- A used pre-v2 MiniMax H3 license may migrate after an OS reinstall only through explicit `legacyRecovery.mode=os_reinstall`: require possession of the original code, high-confidence system UUID plus strong motherboard digests, matching historical MAC tail when present, and an atomic one-time v2 bind that preserves `activatedAt` and activation count. Existing-v2 or insufficient/mismatched hardware must remain HTTP 409; legacy clients without this field keep the original exact-device behavior.
- Desktop clients may enter the second legacy-license recovery stage only after the normal redeem request returns the exact trigger `409 LEGACY_RECOVERY_REQUIRED`; no other 400/409 may cause an automatic `legacyRecovery` retry.
- `ACTIVATION_CODE_ENCRYPTION_KEY` is the shared activation-code encryption root for Vercel and Tencent. Used legacy records may be rotated only after an explicit porcelain-dialog confirmation and must retain product, device, activation time, hardware binding, and existing offline receipt.
- Every browser-to-COS upload ticket must reconcile the bucket CORS rule for both official domains and the deployment's HTTPS `APP_ORIGIN` before signing; Tencent direct-IP production must remain a supported upload origin, and signed URLs must never appear in client diagnostics.
- The embedded short-drama product must use the Gulong website as its only account UI: signed-in users enter the studio directly, while signed-out users see the website's `AccountModal`; never expose the short-drama app's own login or registration card inside the iframe.
- Every production update to `main` must pass the repository quality gate and publish the same commit to both Vercel Production and the Tencent Debian node through the audited dual-target workflow. Tencent activation must remain atomic and automatically restore the previous healthy release on a failed restart or health check; deployment credentials never belong in Git.
